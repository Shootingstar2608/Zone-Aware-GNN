# HCM-Sim v1 — Dataset and Benchmark Specification

**Status:** Proposed release contract for `HCM-Sim v1.0-rc1`  
**Owner:** Research lead / integration owner  
**Scope:** Dataset and evaluation contract only. This document does **not** prescribe or modify model architecture.

## 1. Research positioning

HCM-Sim is a **synthetic, rule-based traffic forecasting benchmark** over a
road graph and functional-zone semantics derived from Ho Chi Minh City data.
It is not an observed TomTom traffic dataset and must not be described as
real-world traffic measurements in papers, README files, figures, or result
tables.

The benchmark supports controlled study of Non-IID spatiotemporal forecasting:
quantity skew, zone skew, temporal shift, concept drift, and input masking.
The static graph and zone labels are based on OSRM/OSM-derived inputs; dynamic
traffic features and targets are generated by the HCM-Sim simulator.

## 2. Canonical data sources and paths

| Component | Canonical source | Purpose |
|---|---|---|
| Static road graph | `data/raw/hcm_osrm_dataset.csv` | Build adjacency `A` and free-flow reference |
| Functional zones | `data/raw/zone_labels.csv` | Build multi-label zone tensor `Z` |
| Dynamic traffic | HCM-Sim generator | Build input `X` and target `Y` |

The canonical HCM-Sim v1 paths are:

```text
data/generated/hcm_sim_v1/hcm_sim_traffic.csv
data/generated/hcm_sim_v1/hcm_sim_traffic.meta.json
data/processed/hcm_sim_v1/graph_dataset.pt
data/processed/hcm_sim_v1/meta.json
data/processed/hcm_sim_v1/manifest.json
```

`data/raw/tomtom_traffic.csv`, legacy `data/processed/graph_dataset.pt`, and
their historical results are not inputs to the HCM-Sim v1 paper benchmark.
Observed TomTom data, if collected in the future, must live in a separately
documented private/external-validation track and must never be silently mixed
with HCM-Sim.

## 3. Generation and build contract

Generate dynamic synthetic traffic with an explicit seed and output path:

```bash
python scripts/dev/generate_synthetic_traffic.py \
  --seed 42 --days 7 \
  --out data/generated/hcm_sim_v1/hcm_sim_traffic.csv
```

Build the dataset without overwriting legacy data:

```bash
python scripts/build_graph.py \
  --traffic-path data/generated/hcm_sim_v1/hcm_sim_traffic.csv \
  --out-dir data/processed/hcm_sim_v1 \
  --t-in 12 --t-out 24
```

The simulator must record `data_source: synthetic`, simulator name/version,
seed, start time, sampling interval, and generated duration in its metadata.
The build step must record SHA-256 hashes of all inputs, the Git commit, output
dimensions, `T_in`, and `T_out` in `manifest.json`.

## 4. Dataset schema and model compatibility

Every `graph_dataset.pt` for HCM-Sim v1 must contain the following required
fields. Existing models must remain compatible with the first five fields.

| Field | Type / shape | Requirement |
|---|---|---|
| `A` | float tensor `(N, N)` | Row-normalized directed adjacency |
| `Z` | float tensor `(N, K)` | Binary, multi-label zone indicators |
| `X` | float tensor `(S, N, T_in * F)` | Input traffic windows |
| `Y` | float tensor `(S, N, T_out)` | Future congestion-ratio targets |
| `time_labels` | long tensor `(S,)` | Discrete time class, backward-compatible input |
| `hour` | long tensor `(S,)` | Exact hour in `[0, 23]` |
| `dow` | long tensor `(S,)` | Day of week in `[0, 6]`, Monday = 0 |
| `time_sinc` | float tensor `(S, 8)` | Cyclical hour/day encoding |
| `nodes` | list | Node names in tensor order |
| `feature_names` | list | Ordered input feature names |
| `zone_types` | list | Ordered zone-label names |

The four dynamic features are ordered as:

```text
0 congestion_ratio
1 traffic_delay_s
2 travel_time_s
3 ff_ratio
```

Default benchmark geometry is `T_in=12`, `T_out=24`, and a 15-minute sampling
interval. The sample-count invariant is:

```text
S = T - T_in - T_out + 1
```

## 5. Time-label contract

All HCM-Sim v1 datasets must contain and validate all four labels:

| Label | Integer | Hour range |
|---|---:|---|
| night | 0 | 00:00–05:59 |
| rush_morning | 1 | 07:00–09:59 |
| rush_evening | 2 | 16:00–19:59 |
| normal | 3 | all remaining hours |

`time_labels`, `hour`, and `dow` must be derived from the same timestamp. Any
dataset that is missing one of labels `0, 1, 2, 3` fails release validation.

## 6. Evaluation protocol

All headline HCM-Sim results must use:

1. Chronological train/validation/test split.
2. Purge gap `T_in + T_out - 1` between adjacent splits.
3. Normalizers fit on the train split only.
4. The same train-fitted normalizers applied to validation and test data.
5. Inverse-transformed predictions and targets before MAE, RMSE, MAPE, and
   WAPE are reported.
6. At least 10 model seeds for final tables, with mean, standard deviation,
   95% confidence interval, effect size, and Holm-corrected significance tests.

Random-split results may be retained under `legacy/` solely for historical
comparison and must never appear in a main paper result table.

## 7. Benchmark scenarios

The v1 release evaluates the following controlled scenarios:

| Scenario | Controlled factor | Required measurements |
|---|---|---|
| IID chronological | Standard clean forecast split | MAE, RMSE, MAPE, WAPE |
| Quantity skew | Observation imbalance by node | Gini, coverage, metrics |
| Zone skew | Zone-cluster distribution shift | Cluster divergence, metrics |
| Temporal shift | Weekday-to-weekend transfer | Relative degradation |
| Concept drift | Incident magnitude/duration/ramp | Recovery and degradation |
| Input masking | Missing node/time observations | Missing rate, imputation strategy, metrics |

Each scenario must include its dataset fingerprint, partition parameters, seed,
split indices, purge gap, generator Git commit, and `mask_hash` where relevant.

## 8. Release gates

HCM-Sim v1.0-rc1 is ready for experiments only when all conditions hold:

- `pytest -q` passes.
- Dataset generation and build succeed from a clean checkout.
- The four time labels are present and match their hours.
- Partition metadata is reproducible bit-for-bit.
- No document calls HCM-Sim observed TomTom traffic.
- A smoke experiment runs against `data/processed/hcm_sim_v1` using chrono
  split and train-only normalization.

## 9. Explicit limitations

HCM-Sim does not establish performance on observed real-world traffic. Zone
effects are simulator assumptions, so a zone-aware method can exploit an
inductive bias aligned with the generator. The benchmark must therefore report
held-out simulator mechanisms and, before a strong real-traffic claim, require
external validation on public or properly licensed observed traffic data.
